# Risk register

MouldShield, team THE SHARKS. Kept by the Scrum Master (Adrian) and checked at every sprint review. Last updated: 27 October 2026.

The first risks come from our proposal and Formative 1. New risks are added when we find them. Closed risks stay in the table, so we can see how they were handled.

## Open risks

| ID | Risk | Level | Owner | What we do |
|----|------|-------|-------|------------|
| R1 | The device breaks before the viva | Medium | Sergiu | The data simulator (T09) sends realistic readings, so the dashboard and the demo still work |
| R2 | The university Wi-Fi blocks the device | Low | Adrian | We decided not to use the university Wi-Fi. The device always connects through Adrian's phone hotspot, which worked in class on 15 Oct. Adrian keeps the phone charged, and we check the connection again the day before the viva |
| R3 | We fall behind | High | Adrian | We follow MoSCoW and cut from the bottom of the backlog (Should items first). Progress is checked at every sprint review |
| R6 | A firmware update breaks the TLS clock workaround (found 13 Oct) | Medium | Adrian | We stay on firmware v2.5.3. After any update, we test the AWS connection again (part of T21). Bug reported to M5Stack as [uiflow-micropython#120](https://github.com/m5stack/uiflow-micropython/issues/120) |
| R7 | The AWS credit runs out, for example if the server is left running | Medium | Adrian | Free plan (cannot be charged) and budget alert at $20 a month. The EC2 server runs since 27 Oct (T16). It is a small `t3.micro`, CloudFront stays inside its always-free tier. Decided on 28 Oct: the server stays on until the viva, so the live dashboard and the QR code always work; the credit (about $179 on 28 Oct) is checked every day. The Elastic IP is still charged a little while the server is stopped |
| R9 | Readings are lost when part of the system is down. Found in the R8 tests on 21 Oct (4 to 9 readings lost each time the connection dropped) | Low | Adrian | Device side fixed on 21 Oct: the device keeps up to one hour of readings in memory and sends them in order when the connection is back (tested: 4 readings kept during a 1 minute drop, all saved, `GET /verify` OK with 131 readings). Still open: a reading that reaches the subscriber while the API is stopped is lost, and the waiting readings are lost if the device is switched off. Seen again on 27 Oct: while the EC2 server restarts (about 25 seconds) or is stopped, AWS IoT Core does not keep the readings for the subscriber, so they are lost |
| R10 | Someone sends a huge number of requests to the public dashboard (flood or DoS) | Low | Adrian | From outside only GET and HEAD are allowed, plus the photo upload and the report, which have daily limits (R14), so no reading can be changed or added. CloudFront includes AWS Shield Standard for free. We did not add AWS WAF with rate limiting, because it would cost about $14 a month. Future work for a real version |
| R11 | The traffic between CloudFront and the EC2 server is plain HTTP, not HTTPS | Low | Adrian | The users only get HTTPS (CloudFront redirects HTTP to HTTPS), and port 80 on the server only accepts CloudFront. The part that is not encrypted goes between CloudFront and our server. Future work: HTTPS to the server, or a CloudFront VPC origin so the server has no public port at all |
| R12 | The data simulator (T09), our backup if the device breaks (R1), could not send readings to the EC2 server: its address was fixed to `127.0.0.1:8000/readings`, but on the server the API is on port 80 under `/api` | Low | Adrian | Found and fixed on 27 Oct: the simulator now reads the address from `MOULDSHIELD_API_URL`, like the subscriber, and the default still works on our own computers. Tested with the same setup as the server (both addresses work, `GET /verify` OK). Not run on the real server on purpose, because its readings would go into the real hash chain for good. How to run it there: `deploy/README.md` |
| R13 | Photos are personal data: they show the inside of a home, and the location saved with them is the address of the tenant | Medium | Adrian | Added with T18 on 27 Oct. Photos are stored in a private S3 bucket without their hidden data. The location stays only in the database on the server and the API never sends it back (a test fails if it ever does). Anyone with the dashboard link can see the photos and their description, so in the demo we only use test photos. A real version would need sign-in for tenants. Found in our iPhone test on 27 Oct: iOS removes the location (and often all EXIF data) when a photo is chosen in a browser, so for most iPhone users the address never reaches us |
| R14 | Someone uploads many photos or asks for many reports to spend our AWS credit on Bedrock | Low | Adrian, Sergiu | Photos: at most 20 calls to Bedrock in any 24 hours, counting also the photos the tenant does not keep, 15 MB each, only image files, Bedrock only called after the file is checked. Reports: at most 50 calls in any 24 hours, then a fixed text; each explanation is saved and used again for the same reading and language |
